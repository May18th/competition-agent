# 可创无限开发基线与迭代流程

版本：2026-10-02
用途：作为后续功能开发、验收、部署和协作的唯一流程基线。

## 1. 产品边界

可创无限是“用户提供真实创意、草稿和数据，系统协助组织材料”的竞赛申报工作台，不替用户虚构事实，也不以生成字数代替材料质量。

用户主流程固定为：

```text
提交创意/草稿
  -> 选择赛事与生成档位
  -> 规则与来源核验
  -> 生成申报材料草稿
  -> 评审诊断与待核实清单
  -> 用户局部修改/补充真实数据
  -> 统一导出 Word/PDF/PPT/ZIP
  -> 导出前质量检查与可追溯记录
```

系统应协作用户完成材料，而不是代替用户做事实判断、署名决定或提交决定。

## 2. 交付开发顺序

任何新功能必须按以下顺序完成，不能跳过契约或验收直接堆代码：

### 阶段 A：PRD 与验收标准

- 写清目标用户、使用场景、输入、输出、失败状态和不做什么。
- 为桌面端、移动端分别写出关键交互验收条件。
- 明确真实数据、测算数据、待核实数据三种状态。
- 明确导出物页数、目录层级、表格结构、文件名和来源标注规则。

### 阶段 B：任务拆解

将需求拆为可独立验收的任务：数据模型、后端接口、前端状态、导出、测试、部署。每个任务必须有负责人、输入依赖、完成条件和回滚方式。

### 阶段 C：数据模型与 API 契约

- 先确定 SQLite 表、字段、状态枚举和错误码。
- 再确定请求/响应 JSON 示例和兼容策略。
- 前后端只通过契约通信，不在前端复制后端业务规则。
- 局部修改必须以 `history_id + module_key + replacement` 为最小更新单位，不得重新跑完整生成。

### 阶段 D：后端实现与测试

- 先实现持久化、幂等、超时、重试和错误记录。
- 生成流程必须返回任务 ID、阶段、部分结果和可读失败原因。
- 每个接口先有单元测试/接口探针，再接前端。
- 导出统一读取同一份结果快照，Word、PDF、PPT、ZIP 不得各自重新生成内容。

### 阶段 E：前端接入

- 前端只消费 API 契约，不通过 DOM 猜测后端状态。
- 所有按钮都有 loading、disabled、成功、失败、超时和可重试状态。
- 弹窗、菜单、Toast 必须有键盘、触摸和遮罩关闭路径。
- 桌面端和移动端使用同一状态源；只允许布局差异，不允许数据口径差异。

### 阶段 F：全链路验收与发布

按“空输入、最小输入、完整输入、网络中断、模型超时、导出失败、移动端窄屏、桌面端宽屏”八类场景回归。通过后才生成发布包、备份线上文件、部署和公网复验。

## 3. 当前架构治理方向

现有代码先保持线上稳定，再逐步治理，不进行一次性重写：

1. `backend/app.py` 只保留应用装配和路由兼容层；新增业务优先放入 `backend/services/`、`backend/repositories/`、`backend/contracts/`。
2. 生成任务统一由任务服务管理，Agent 通过消息/事件通信；禁止新代码直接从一个 Agent 调另一个 Agent 的内部函数。
3. 导出统一由结果快照和产物清单驱动，避免 Word/PDF/PPT/ZIP 各有一份字段清单。
4. 前端保留现有视觉风格，新增功能优先抽成小型组件函数；禁止继续增加大型内联脚本和重复按钮。
5. 历史数据、上传文件、`.env`、数据库和生成目录与代码包分离，发布包不得覆盖这些运行数据。

## 4. 统一数据状态

所有事实型字段必须携带以下元数据：

```json
{
  "value": "字段值",
  "status": "user_provided | sourced | estimated | needs_verification",
  "source": "来源名称或用户材料",
  "source_url": "可选公开链接",
  "as_of": "数据日期",
  "confidence": "high | medium | low"
}
```

`estimated` 和 `needs_verification` 不得在导出时伪装成实测值；用户补充后，只更新对应字段及依赖图表。

## 5. 统一错误处理

后端错误必须包含稳定的 `code`、用户可读的 `message`、内部 `detail`、`retryable` 和 `task_id`。前端展示人话说明，但不向用户泄露堆栈、密钥或内部路径。所有失败写入失败记录，管理员可按任务查看完整原因和重试次数。

## 6. 发布门槛

每次代码修改至少通过：

```text
node --check frontend/static/app.js
python -m compileall -q backend
git diff --check
接口健康检查 /api/health
静态资源版本号更新
线上服务 active
公网首页与静态资源 HTTP 200
```

涉及生成或导出的改动，还必须补充真实接口探针和产物内容检查。未通过的项目只能标记为“待验收”，不能写“已完成”。

## 7. 当前第一批治理任务

1. 建立 `services/repositories/contracts` 三层目录和最小示例。
2. 把生成任务、状态、失败记录和导出产物清单写入统一契约。
3. 修复简洁版/深度版缺失模块和重复标题，确保二次生成不丢板块。
4. 统一 Word 为源文档，PDF 由 Word 结果转换，PPT/图表引用同一结果快照。
5. 为后台失败详情、反馈分页、生成任务状态增加接口级回归测试。
6. 完成桌面端与移动端的同一条真实流程回归后再做视觉微调。
