## 0.5 ⚠️ 最重要的一条边界：创意生成 vs 申报表优化

用户 2026-09-25 明确强调（原话）：

> 「这个申报表规则仅限于创意的，优化申报表的原则是不改变原来申报表的格式和排版，只修改内容。」

**必须区分两条链路，绝不能混用：**

| 链路 | 场景 | 用什么 | 关键原则 |
|---|---|---|---|
| **A. 创意生成** | AI 从零写出申报书 / 报告 / 分析 / 大纲 | `docx_render.build_docx()`（套格式标准） | 可以按标准排版：宋体黑体、目录、封面、页码 |
| **B. 申报表优化** | 用户上传**已有**申报表，AI 改内容 | `docx_inplace.apply_content_keep_style()` | **原表格的格式排版一律不动，只换文字** |

链路 B **绝对不能**用 `docx_render` 重新渲染 —— 那会把用户原来的表格结构、合并单元格、字体、页边距全部冲掉。

### B 链路现在的实现（我刚重写，Codex 只需接线）

```python
from docx_inplace import apply_content_keep_style

buf, report = apply_content_keep_style(original_bytes, optimized_text)
# buf      -> 直接 send_file 给用户
# report   -> {'slots': 51, 'items': 5, 'replaced': 5, 'appended': 0, 'untouched': 46}
```

它做的事：
- 按文档真实顺序遍历 `w:p` 和 `w:tbl`，**表格单元格也参与替换**（旧代码完全不碰表格，申报表内容基本在表格里）
- 只改 `run.text`，**字体/字号/颜色/加粗/缩进/边框/底纹全部不动**
- 优化文本比原文长时，**多出来的追加到末尾，绝不丢内容**（旧代码是直接丢弃）
- 优化文本比原文短时，剩余位置**保持原文不动**

实测（用真实的《赛事规则解析报告.docx》）：52 段结构不变，Title 20pt / Heading1 16pt 格式原样保留，文字已替换。

### 给用户一个「要不要替换」的开关（用户 2026-09-25 要求）

用户原话：**「或者可以加一个选项，让用户自行选择要不要替换」**。

请在 `export_original_format` 上支持 `mode` 参数，前端给一个二选一：

| mode | 行为 | 默认值 |
|---|---|---|
| `keep`（保留原格式） | 调 `docx_inplace.apply_content_keep_style()`，原位换字，格式排版不动 | ✅ **默认** |
| `reformat`（按标准重排） | 调 `docx_render.build_docx(..., doc_type='default')`，套申报书标准格式（带封面/目录/页码） | 用户主动勾选才走 |

建议前端文案：
> 导出方式：**保留原表格格式，只替换内容**（推荐） / 按标准格式重新排版

接口示意：
```python
mode = request.form.get('mode', 'keep')
if mode == 'reformat':
    doc = build_docx(title, optimized_text, doc_type='default',
                     subtitle=..., school=..., team=..., advisor=...)
    ...
else:
    buf, report = apply_content_keep_style(original_bytes, optimized_text)
```

### 需要 Codex 配合的一点（prompt 约束）

为了让「一一对应」更准，请在优化类 Agent 的提示词里要求：

> 优化输出必须**保持原申报表的条目结构一一对应**：不合并条目、不拆分条目、不新增条目、
> 不加 Markdown 标题符号，每一条只输出改写后的文字。

这样 `slots` 和 `items` 数量能对上，替换最精准。

### ⚠️ 版式不动 ≠ 内容不动

用户进一步明确（原话）：**「申报书的内容也是改的啊，除了格式排版其他都改，版式不要动，内容改」**。

所以两条都要成立，别做成"为了保格式就不敢改内容"：

| 要改 | 不要动 |
|---|---|
| 文字内容（必须实质优化：更充实、更专业、更有说服力） | 表格结构、行列数、合并单元格 |
| 表述、用词、逻辑 | 字体、字号、颜色、加粗、对齐 |
| | 边框、底纹、页边距、页眉页脚、页码 |

**一个必须注意的副作用**：内容写太长会把表格单元格撑变形，等于变相改了版式。
所以请在提示词里加长度约束：

> 每条优化后的文字长度应与原条目**大致相当（建议 ±30% 以内）**，
> 宁可精炼也不要大幅膨胀，避免撑破原表格版式。

## 2. Codex 要做的第 2 件事：内容层提示词改造（这是重点）

格式只能让文档"好看"，**用户真正不满的是内容太单薄**。以下全部来自用户原话，请逐条落到 `competition_agents.py` 的提示词里。

### 2.1 报告类（proposal / 各类 report / rich_deck 里的报告性章节）

**必须满足：**

1. **必须有三级目录**，且三级标题要用**正式短语**，**不能是句子**。
   - ❌ 错误：`## 我们的项目是怎么解决老人摔倒问题的`
   - ✅ 正确：`## 二、技术方案` → `### （一）多模态感知层`
2. **结构必须完整**：`摘要 / 背景 / 内容 / 分析 / 总结 / 展望` 一个都不能少。
3. **严禁短句、严禁几句话就写完**。每个小节要写成**完整的大段文字**（一段 150～400 字），
   有论点、有展开、有数据或事实支撑。用户明确说：**"严禁几句话就写完，严禁短句，要写一大段完整的大段文字"**。
4. **严禁整篇用序号形式罗列**（不要 `1. xxx  2. xxx  3. xxx` 这种清单体）。
   用户明确说：**"不要序号形式的"**。
   - ❌ 错误：整节写成 `1. 成本低  2. 效率高  3. 易部署`（三行就没了）
   - ✅ 正确：把三点写成一段连贯文字——"本方案在成本、效率与部署三方面具备显著优势。成本方面……
     效率方面……部署方面……"，**用文字串起来，而不是用序号列出来**。
   - 允许例外：确实需要逐条对比的（如评分维度表、参数对比）用 **Markdown 表格**，而不是序号列表。
5. **要有完整分析，不要只给结果**。
   - ❌ 错误：`创新性得分 30 分。`
   - ✅ 正确：先说评分依据 → 再展开技术细节 → 再对比同类方案 → 最后点出优势与风险，写成段落。
6. 表格用**标准 Markdown 表格**输出（`| a | b |` + `|---|---|`），渲染器会转成真 Word 表格。
7. **要有实实在在的内容**：报告里要有具体的技术细节、数据、案例、对比，不能通篇是"本项目具有创新性"这类空话。

### 2.2 分析类（competitor_analysis / business_model / risk_analysis / judge_feedback / diagnosis）

- **必须分段阐述**，不能只有结论清单。
- 每个分析维度：现状 → 原因 → 影响 → 应对，写成段落，不要一句话一行。
- 不要出现"综上所述"一句话收尾就结束的情况。

### 2.3 大纲类（ppt_outline / speech_script 的大纲部分）

- **最轻最简**：只要层级清晰的条目，**不要段落、不要大段阐述**。
- 每页/每条一行短语，不要写完整句子。
- 用户原话：**"大纲不要段落、不要大段阐述"**。

### 2.4 通用红线

- **目录里的三级标题不要是句子**，要像"1.1 技术架构"这种正式条目。
- 报告里**严禁**出现"以下是……"这种口水过渡句堆篇幅。
- 内容宁可长，不可短。用户明确表示：**短 = 质量差**。

### 2.5 建议的实现方式

在各 Agent 的 system/user prompt 里加一段**输出规格约束**，例如：

```
【输出规格 —— 必须遵守】
1. 使用 Markdown，最多三级标题（## / ###），一级用「一、二、三、」，二级用「（一）（二）」，三级用「1. 2. 3.」
2. 三级标题必须是正式短语，不是完整句子
3. 结构必须包含：摘要 / 背景 / 内容 / 分析 / 总结 / 展望
4. 每个小节必须写成 150～400 字的完整段落，有论点、有展开、有依据；严禁一句话一段、严禁短句罗列
5. 分析类内容必须给出「现状→原因→影响→应对」的完整链条，不能只给结论
6. 表格用标准 Markdown 表格语法
7. 全文中文标点用全角
```

并在 `_run_generation` 或后处理里加一个**长度自检**：
若某章节正文 < 150 字，记录 warning 日志（方便我们后续定位是哪个 Agent 偷懒）。
