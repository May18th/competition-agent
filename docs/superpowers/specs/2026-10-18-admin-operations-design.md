# 后台运营工作台设计

## 目标

把管理后台从“看数字”升级为“发现问题、定位原因、推动处理”的运营工作台，同时保持前台生成、聊天和导出流程不变。

## 范围

- 统一 `/admin`、`/admin/panel`、`/monitor`、统计 API 的数据口径。
- 展示生成质量、导出质量、Token 用量、失败模式和告警。
- 完善反馈/工单处理状态与审计。
- 对历史记录中的未收录赛事只做展示层过滤和规范化，不删除原始数据。
- 增加日志与业务数据的留存策略配置，但不在本期自动删除用户作品。
- 将后台静态资源和图表按需加载；不进行一次性大规模蓝图拆分。

## 非目标

- 不修改前台生成算法、模型选择、配额规则、导出质量门核心判定。
- 不删除或覆盖生产数据库、用户作品、回滚备份和运行产物。
- 不把演示只读账号升级为写权限。

## 数据语义

1. 统计范围由统一的 `admin_scope` 计算：时间范围、排除测试记录、正式赛事目录过滤由同一处决定。
2. 历史表保留原始 `competition_name`；后台展示使用正式赛事名，别名归并，未收录名称隐藏并计入质量提示。
3. 质量指标区分成功、软警告、硬拦截、渲染失败和恢复成功，不用“生成成功”替代“可交付成功”。
4. Token 统计只展示脱敏用户键，不展示原始 UID、密码、Token 或申报书正文。
5. 审计日志记录登录、工单状态变化、导出和数据导出动作，支持轮换；不把用户输入直接当作日志格式控制符。

## 工作台信息架构

- 顶部：时间范围、当前角色、服务健康、额度与告警。
- 核心指标：生成量、可交付率、质量门拦截率、平均耗时、Token 消耗。
- 诊断区：质量弱项、失败模式、赛事资料缺口、逾期工单。
- 处理区：反馈/工单筛选、优先级、状态、回复、审计记录。
- 明细区：生成记录、导出记录、Token 使用、原始数据导出。

## 发布约束

- 先在隔离 worktree 写测试和实现。
- staging 8081 回归通过后，再以 fast-forward 更新生产 8080。
- 验证 systemd 服务、工作目录、提交号、健康接口和页面/API 行为。
