# 系统架构说明

> 项目：科创赛事多智能体协同创作助手
> 编写：成员 A（技术负责人）
> 版本基准：2026-09-25 / app.py 1411 行、competition_agents.py 727 行、index.html 893 行

## 一、一句话定位

面向大学生科创竞赛团队的**端到端申报材料生成系统**：用户只提交「赛事名称 + 项目创意（可选草稿）」，系统自动走完「规则解析 → 同质化检测 → 申报书生成 → 模拟评审 → 诊断 → 答辩材料」全链路，产出可直接下载的 Word / ZIP 材料包。

## 二、技术栈与版本

| 层 | 选型 | 版本 | 选型理由 |
|---|---|---|---|
| 前端 | 原生 HTML/CSS/JS（无框架） | — | 单人可维护，无构建环节，断网也能跑（依赖已本地化） |
| Markdown 渲染 | marked | v15.0.12 | CDN + 本地 `static/marked.min.js` 双路兜底 |
| 可视化 | ECharts | 5.4.3 | CDN + 本地 `static/echarts.min.js` 双路兜底 |
| Web 服务 | Flask | 3.x（Werkzeug 3.1.8） | 轻量，自带 `/static` 路由，单文件即可部署 |
| Agent 编排 | **LangGraph** | **1.2.12** | 有状态的图式编排，原生支持条件边与扇出/扇入；比纯 Prompt 链可靠 |
| LLM 接入 | langchain-deepseek | 1.1.1 | 官方适配器，切换模型只改一处 |
| 模型 | deepseek-chat | temperature 0.3 / max_tokens 6000 | 中文长文性价比高，响应快；0.3 抑制套话 |
| 持久化 | SQLite | 内置 | 历史记录单表存储，零运维 |
| 文档导出 | python-docx | ≥1.1.0 | 生成 .docx 供二次编辑，比 PDF 更适合申报场景 |
| PDF 解析 | pypdf / pdfplumber | ≥4.0 / ≥0.11 | 赛事规则 PDF 与用户草稿上传解析 |

> ⚠️ 口径修正：`requirements.txt` 写的是 `langgraph>=0.2.0`，实际运行版本是 **1.2.12**，答辩按实际版本讲，requirements 需同步改成 `langgraph>=1.2.0`。

## 五、State 字段设计

`CompetitionState`（TypedDict，22 字段）分四类：

- **输入**：competition_name、idea、rule_content
- **中间结果**：parsed_rules、similarity_report、competitor_analysis、business_model、risk_analysis、tech_solution、implementation_plan、social_value、project_summary、proposal
- **评审**：judge_feedback、proposal_analysis、defense_questions、ppt_outline、speech_script、one_liner、score
- **控制**：revision_count、approved

设计要点：**所有节点读写同一份 State**，节点间不直接传参——这是能无条件增删节点、也能做条件回边的前提。代价是并行改造时存在写冲突风险，需改为增量返回或配 reducer。

## 六、一次深度版请求的完整时序

1. 前端取 `competition / idea / proposal_draft / mode`，POST `/api/generate`
2. 后端把 `proposal_draft` 拼进 `idea`（`app.py` 1066 行），组装初始 State
3. 调用 `deep_app.invoke(state)`，LangGraph 依次执行节点；每次 LLM 调用经 langchain-deepseek 打到 DeepSeek
4. `judge` 打分 → 写 score / approved；`should_iterate` 判定：未过且 revision_count < 1 → 回 `writer` 重写一轮（此时带上上一版 + 评委意见）
5. 通过后依次产出 defense / ppt / speech
6. 结果落 SQLite 历史，同时 JSON 返回前端
7. 前端填充 5 个 Tab；深度版额外初始化 3 个 ECharts 图
8. 导出：前端 POST 对应字段 → 后端 python-docx 生成 → `/api/export_zip` 打包下载

## 七、关键设计决策与权衡

| 决策 | 为什么 | 代价 |
|---|---|---|
| 用 LangGraph 而非顺序脚本 | 条件回边（迭代改写）与并行扇出由框架保证，改链路不动业务代码 | 引入框架学习成本 |
| 共享 State 而非参数传递 | 节点可插拔、可任意重排 | 并行需改造为增量写入 |
| 双版本流水线（简洁/深度） | 覆盖「先看看效果」与「要成稿」两种诉求 | 两条图要各自维护，简洁版出现孤儿节点 |
| 模型选 DeepSeek | 中文长文成本低、响应快，适合学生团队 | 深度推理能力弱于旗舰模型，靠 temperature 与 prompt 约束补 |
| 导出 docx 而非 pdf | 申报材料需要二次编辑 | 无法保证格式一致性，需要模板约束 |
| 前端零框架 | 不需构建，断网可演示，交付简单 | 代码层面缺少组件化，内联样式偏多 |

## 八、当前架构债清单

1. 简洁版 7 个孤儿节点（见第四节）
2. 深度版 competitor→business→risk→tech→plan→social→summary 七节点**硬串行**，实测各节点只读 `idea`，无依赖关系，可并行改造
3. 赛事知识库覆盖 **4 / 11**（缺 7 个赛事的评分标准文本）
4. `app.py` 内嵌一份约 6 万字符的失效 HTML 副本，与真实 `index.html` 并存，有误改风险
5. 生成链路**无超时中断**，单次请求最长可达数分钟
6. 评委分数被 prompt 锁在 60-85 分区间，且用正则抓取全文首个「数字+分」，存在误取风险
