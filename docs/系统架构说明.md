> 版本基准：2026-11-25
> 本文所有数字均为当日实测（`wc -l` / `grep -c` / 服务器 `sqlite3` 查询），不是估算值。
> 上一版（2026-09-25）记录的 app.py 1411 行、index.html 893 行已全部过期，本版整体重写。

## 一、定位与边界

面向大学生科创竞赛团队的**申报材料生成系统**。输入是「赛事名称 + 一句创意（可选草稿）」，输出是一套符合该赛事官方评审规则的申报书、答辩问题、PPT 大纲、竞品与商业分析，可直接导出 Word / PDF / PPTX / ZIP。

它不是通用写作工具，差异在三个约束上：

1. **结构来自官方规则，不来自模型想象**——每个赛事的章节顺序、评分维度与权重、字数区间、是否双盲，都存在结构化档案里，写作前注入。
2. **出稿必须过质量门**——空文档、乱码、占位符残留、编造引用、双盲信息泄露会被拦在导出前，不给下载。
3. **不追求"生成得像"，追求"按评分表得分"**——内置模拟评委按赛事维度打分，低分打回重写。

**明确不做**：不做赛事报名、不做作品提交、不代替用户做技术判断。生成内容是初稿，需作者二次修改，这一点在结果页与页脚均有明示。

## 四、一次生成请求的完整生命周期

| 步 | 发生什么 | 位置 |
|---|---|---|
| 1 | 前端校验「赛事 + 创意」，POST `/api/generate_async`（带 `mode: fast｜deep`） | `app.js` |
| 2 | 服务端取 `uid`、查当日配额、过限流（用户桶 + 出口 IP 桶）、检查并发队列 | `app.py:4657` 起 |
| 3 | 建任务记录（内存 `tasks` + `run_registry` 落库），立即返回 `task_id` | `_start_generation` `app.py:4515` |
| 4 | daemon 线程写入线程本地上下文（`task_id / user_id / mode`），组装 State，调 `fast_app.invoke` 或 `deep_app.invoke` | `app.py` worker |
| 5 | 图内节点并行/串行执行；每个节点开始与结束都 `report_stage`，SSE 与轮询都能读到 | `stage_reporter.py` |
| 6 | 每次 LLM 调用经包装层记账（配额 + token + 模型 + 阶段），落 `llm_usage` 表 | `competition_agents.py` 包装区 |
| 7 | 出稿后过篇幅闸门（不足补写 / 超限整句裁剪），跑清理链去套话与占位段 | `competition_agents.py` |
| 8 | 结果落 `history`（正文 + 结构化字段 + 图表数据），前端拉 `result_data` 渲染 | `app.py` |
| 9 | 用户点导出 → 过质量门 → 渲染器生成文件 → 下载；同时回填 `run_registry` 的导出状态 | `app.py:2204` 起 |

关键设计：**生成是异步的，导出是同步的**。生成可能跑 3~5 分钟，必须能断线重连；导出必须当场拿到文件或当场被拒。

## 五、编排层：LangGraph 双工作流

### 5.1 简洁版（12 节点）

```
START ─┬─→ rule_parser ────────┐
       ├─→ similarity_checker ─┤
       ├─→ idea_evaluator ─────┼─→ analysis ─→ writer ─┬─→ judge ──(条件)──→ defense ─→ speech ─→ END
       └─→ one_liner ──────────┘                       │                   └─→ ppt ────┘
                                                       └─→ proposal_analysis ─→ END
```

前 4 个节点**同时启动**（都只读输入，互不依赖），一起汇入 `analysis`。
`judge` 后接条件边：分数不达标且还有迭代额度 → 回 `revise` → 再回 `judge`；达标 → 扇出 `defense` 与 `ppt`，两者汇入 `speech`。

### 5.2 深度版（19 节点）

```
START ─┬─→ rule_parser ──────────┐
       ├─→ similarity_checker ───┤
       ├─→ idea_evaluator ───────┤
       ├─→ one_liner ────────────┤
       ├─→ competitor ───────────┤     ← 4 路并行分析
       ├─→ business ─────────────┤
       ├─→ risk ─────────────────┤
       └─→ tech ─────────────────┘
                                 ├─→ plan ───┐
                                 ├─→ social ─┼─→ writer → judge → expert_review
                                 └─→ summary ┘        ↓
                                          proposal_analysis / defense / ppt / speech
```

与简洁版的差别：
- 前 4 项分析拆成 `competitor / business / risk / tech` 四路并行，而不是 `analysis` 一次产出（深度版要更细的论证）。
- `plan / social / summary` 三者**并行扇出**再汇入 `writer`。三者都只读创意与检索结果，原来串行会白等两次 LLM 调用。
- `writer` 用 `deep_writer_agent`（更长篇幅、更严的章节约束），并多一个 `expert_review`（多视角挑刺）。

### 5.3 并行节点的线程上下文（踩过的坑）

LangGraph 把同一 superstep 的并行节点分发到线程池执行，**子线程读不到主 worker 线程的 thread-local 变量**。
后果：并行分支上的 LLM 调用查不到当前 `task_id`，用量记录全部丢失。实测过——修复前一次简洁版只记到 5 次调用，`judging`、`idea_scoring` 两个阶段完全没记。

解法：31 个 `add_node` 全部包一层 `_bind_task_ctx(fn)`，从 State 里取出 `_task_id / _user_id / _mode` 重新写入子线程的上下文，执行完清理。

修复前后同一次操作的实测对比：

| | 记录条数 | Token | 覆盖阶段 |
|---|---|---|---|
| 修复前 fast | 5 | 21,345 | 3 个 |
| 修复后 fast | **13** | **46,260** | 10 个全覆盖 |
| 修复后 deep | 24 | 157,436 | 12 个 |

### 5.4 State 设计

`CompetitionState`（TypedDict）分四类字段：

- **输入**：`competition_name`、`idea`、`rule_content`、`mode`
- **中间产物**：`parsed_rules`、`similarity_report`、`competitor_analysis`、`business_model`、`risk_analysis`、`tech_solution`、`implementation_plan`、`social_value`、`project_summary`、`proposal`
- **评审产物**：`judge_feedback`、`proposal_analysis`、`defense_questions`、`ppt_outline`、`speech_script`、`one_liner`、`score`
- **控制字段**：`revision_count`、`approved`、`_task_id`、`_user_id`、`_mode`

铁律：**节点只写自己的字段，不写别人的**。这是并行扇出不会互相覆盖的前提。前端渲染、导出、质检都从 State 的固定字段取数，加节点不影响下游。

### 5.5 条件边

`should_iterate_fast` / `should_iterate` 读 `score` 与 `revision_count` 决定回边还是前进。简洁版默认不迭代（保速度），用户显式传 `iterate=true` 才允许返工一轮。

## 六、领域知识层

| 资产 | 数量 | 内容 | 文件 |
|---|---|---|---|
| 赛事档案 | **15 个** | 章节顺序、评分维度与权重、分赛道权重、字数要求、是否双盲、偏好方向、扣分点、**官方来源 URL + 核查日期** | `assets/data/competition_profiles.json` |
| 官方规则原文 | 15 份 | 从官网/官方附件整理的评分细则文本 | `assets/data/*.txt` |
| 范文库 | 按赛事 | 用于同质化检测与写法提炼 | `kb_samples` 表 + `kb_distill.py` |
| 赛事索引 | 1 份 | 名称/别名的模糊匹配索引 | `static/competition_index.json` |

赛事档案的一条真实结构（iCAN）：

```
name: iCAN大学生创新创业大赛
aliases: [iCAN, ican大赛, AI应用创新挑战赛, ...]      ← 用户随便怎么叫都能匹配
chapters: [项目背景与痛点, 需求分析与目标用户, 开发工具与技术选型, ...8 章]
scoring: [创新性 35, 实用性 25, 原创性 20, 技术方案 20]
scoring_by_track: 创新/创业/挑战三个赛道各自权重（含 source + checked_date）
word_requirement: {official: "PDF ≤20 页且 ≤50MB", suggested: "6000-8000 字 + 6-10 张图"}
double_blind: true                                    ← 决定是否强制脱敏
```

设计要点：**规则可溯源**。每个赛道的权重都带 `source`（官方 URL）与 `checked_date`，官方规则未核实的字段写 `None` 并注明"待核实"，不用猜测值填充。

**prompt 与判据必须同源**：写作 prompt 要求"三处创新：①②③"，判据正则就必须认"三处/三项/创新有三"三种语序。两者不同源时，表现为补写反复失败、复检分数不涨——这个坑踩过一次。

## 七、质量体系（三层，职责不同）

| 层 | 拦什么 | 实现 | 拦截方式 |
|---|---|---|---|
| **L1 生成内检** | 篇幅不足、套话残留、待补写段落、创新点缺失 | `competition_agents.py` 篇幅闸门 + 清理链 + 创新点兜底 | 自动补写/裁剪，不拦截用户 |
| **L2 内容评分** | 按官方维度逐项给分，指出丢分章节 | `scorecard.py`（614 行） | 给建议，用户可选"按评分项补强" |
| **L3 导出闸门** | 空文档/乱码/占位符/编造引用/双盲泄露/格式不合法 | `quality_gate.py`（497 行）+ `_export_review_gate` | **422 拒收，不给文件** |

### L3 的实际覆盖（如实说明）

导出闸门分两层，覆盖并不完全一致：

| 导出接口 | 格式层质检 | 内容评分门（85/80） |
|---|---|---|
| `export_word` | ✓ `check_docx` + 目录校验 | ✓ `_export_review_gate` |
| `export_pdf` | ✓ `check_pdf`（页数/体积上限按赛事） | — |
| `export_pptx` | ✓ `check_pptx` | — |
| `export_zip` | ✓ `check_zip`（文件数/可打开性） | — |
| `export_business` | — | ✓ `score_export` |
| `export_defense` / `export_ppt` / `export_competitor` / `export_all` / `export_original_format` / `export_manifest` | — | — |

结论：**主交付物（Word/PDF/PPTX/ZIP）都有格式层硬拦截；内容评分门目前只在 Word 主稿和商业分析上强制。** 其余接口是辅助材料或打包动作，不重复评分。这条差异是已知的，写在这里是为了答辩时口径一致——不要说成"所有导出都过评分门"。

格式层的判定举例：`check_docx` 会打开产物验证可读、非空、无乱码占位符；`check_pdf` 按赛事档案的页数/体积上限判（如 iCAN 20 页 / 50 MB）；`check_zip` 校验文件件数与可解压性。

## 八、导出与渲染

**没有用模板引擎，直接操作 OOXML。** 原因：申报书要按赛事动态改章节顺序、按评分权重加粗重点、按双盲要求脱敏、插图按数据生成——模板做不到这些组合，最后还是要写代码改 XML。

| 模块 | 行数 | 职责 |
|---|---|---|
| `docx_render.py` | 1315 | Word 正文、标题层级、目录域、表格、页眉页脚、双盲脱敏 |
| `pptx_builder.py` | 1802 | 路演 PPT：封面、章节页、要点页、图表页、备注 |
| `pdf_render.py` | 230 | 中文 PDF 排版（reportlab，自己控字距与断行） |
| `chart_renderer_pro.py` | 743 | 服务端出图：雷达图、趋势图、对比图（matplotlib） |
| `chart_renderer.py` / `chart_render_wb.py` | 439 / 291 | 轻量图表与前端同款配色 |
| `docx_charts.py` | 223 | 把图注入 Word（不依赖 Word 自身绘图） |
| `cover_style.py` | 336 | 封面版式与配色方案 |
| `docx_inplace.py` | 155 | 在用户上传的原始格式上就地替换（保留原样式） |
| `export_guard.py` / `export_recovery.py` | 161 / 142 | 导出前守卫、失败恢复 |

11 条导出路由：`export_word`、`export_pdf`、`export_pptx`、`export_zip`、`export_all`、`export_defense`、`export_ppt`、`export_competitor`、`export_business`、`export_original_format`、`export_manifest`。

`export_original_format` 是差异化的一个点：用户上传自己的草稿，系统按赛事规则重排章节、补缺口，但**保留用户原有样式**，而不是换成系统模板。

## 九、数据层

两个库，职责分离：

| 库 | 体积（实测） | 内容 |
|---|---|---|
| `competition.db` | 27 MB | 16 张表：生成历史、用户、反馈、质检、运行记录、知识库样本等 |
| `llm_usage.sqlite` | 88 KB | 用量明细（每次模型调用一行），独立库是为了高频写不锁主库 |

16 张表按用途分组：

| 用途 | 表 |
|---|---|
| 核心业务 | `history`（333 条生成）、`users`、`uid_sync`、`user_prefs` |
| 对话 | `chat_history`、`chat_profile` |
| 质量与可观测 | `export_reviews`、`gen_failures`、`generation_runs`、`llm_usage`、`issues` |
| 知识库 | `kb_samples`、`kb_meta` |
| 运营 | `feedback`、`shares` |

写入特征：生成过程只写 `generation_runs` 与 `llm_usage`（高频、追加）；`history` 在出稿时一次写入（单条可达数百 KB）。SQLite 用 WAL 之外的单连接短事务，够用。

所有 SQL 走参数化 `?` 占位符（41 处 execute 实测无一拼接用户输入）；动态 WHERE 只拼常量与占位符，日期字段用 `strptime` 严格校验后入参。

## 十、前端架构

### 10.1 形态：零构建

没有 `package.json`、没有 `node_modules`、没有打包器、没有 TypeScript。`index.html` 直接引用 8 个 `<script>`，其中 4 个是本地副本（marked / DOMPurify / ECharts / 自有脚本），CDN 仅作兜底。

| `static/api.js` | **163 行** | 统一请求层：超时、AbortController、错误分档、全局 `onError` |
| `static/scorecard-online.js` | 265 行 | 评分项自查面板：调接口、渲染维度与证据 |
| `static/style.css` | 107 KB | 全站样式（含响应式断点） |
| `static/sw.js` | 1 KB | 自毁型 Service Worker：清缓存并注销自己（避免旧版缓存导致"改了不生效"） |

### 10.3 统一请求层

`api.js` 暴露 `window.WB.api(path, opts)`，做四件事：

1. 默认超时 30 秒，上传 120 秒，可用 `opts.timeout` 覆盖；
2. 有 `AbortController` 就真中断，老内核（早期 iOS Safari / 微信 X5）退化为普通 fetch；
3. 统一解析 `{success, error, code}`，业务错误抛带 `code` 的异常；
4. 全局 `onError` 回调，`app.js` 接上 `wbToast` 做统一提示。

`app.js` 里有 27 处调用收口到这一层，并保留本地兜底函数 `wbApi`（`api.js` 未加载时不至于全站崩）。另有 7 处**故意保留裸 `fetch`**：两处 SSE（读取流不能用统一 JSON 解析）、状态轮询、`demo_sample.json`、`/api/health`，以及 `api.js` 内部实现本身。**生成入口 `generate_async` 显式设 25 秒超时**——之前没设，后台挂起时按钮永久"生成中"，属于死锁级缺陷。

### 10.4 两处流式（SSE）

| 端点 | 事件 | 用途 |
|---|---|---|
| `/api/stream/<task_id>` | `stage`（阶段推进）、`partial`（字段增量）、`done` | 生成过程的打字机效果 |
| `/api/chat` | 逐 token 文本 | 侧边对话 |

实现要点：Flask 侧 `stream_with_context` + `X-Accel-Buffering: no`（否则 nginx 会缓冲住整段响应）；前端用 `ReadableStream.getReader()` 自己解析 `data:` 行，不用 `EventSource`（要 POST 带 body）。

不能用 SSE 时退化为 `/api/status/<task_id>` 轮询，两条路读同一份 `stage_reporter` 状态。

### 10.5 状态与渲染

单页无路由库，靠 `wbPage` 式的显隐切换与 `_lastData` 缓存当前结果。结果区按字段局部渲染，不整页重绘——AI 输出可能几千字，全量重绘会掉帧。

安全：AI 输出先过 DOMPurify 再进 `innerHTML`；Markdown 由 marked 渲染。

### 10.6 为什么没有用 Vue / React（含数据）

这是答辩最容易被问的一条，给实测依据而不是感觉：

| 指标 | 当前（原生 JS） | 引入 Vue/React 后 |
|---|---|---|
| 首屏传输 | 首页 gzip 后 **57 KB**，TTFB 233 ms，完全加载 0.7 s | 至少 +45 KB（Vue 3 runtime）到 +140 KB（React+ReactDOM）gzip |
| 构建环节 | 无。改完刷新即生效 | 需要 node 工具链、`npm install`、产物目录、sourcemap |
| 断网演示 | 全部依赖本地化，可直接演示 | 构建产物可离线，但开发/改样式必须先构建 |
| 交付物可读性 | 评委直接看源文件即可读懂 HTML 结构与请求 | 需要读构建产物或先跑构建 |
| 团队规模匹配 | 单人维护 15,000 行前端 | 组件化收益在多人协作时才明显 |

三条真实理由：

1. **首屏预算**。评委在赛场网络下打开，57 KB 与 200 KB 的差别是"立刻看到"与"等一下"。当前实测 0.7 秒完全加载，加框架后没有一项功能会因此变好。
2. **演示可靠性**。赛场网络不可控，零构建 + 全本地依赖意味着改一个文案不需要 `npm run build` 也不会出现"本地好的、构建后坏了"。
3. **不需要组件化**。这套 UI 是"一个表单 → 一个结果页 → 一组导出按钮"的线性流，没有复杂组件树与跨页共享状态。引入框架主要解决的是多人协作下的状态管理问题，而这是单人项目。

**代价也要说清楚**（不粉饰）：`app.js` 8176 行、300 个函数全在全局作用域，没有类型检查，改错一个变量名只能靠运行时报错发现；DOM 操作分散在各处，没有虚拟 DOM 的统一 diff。这是用"简单"换"可维护性"，在 8000 行这个量级已经开始吃力——如果继续长，第一步应该是拆模块 + 加 JSDoc 类型，而不是直接换框架。

### 10.7 如果一定要上框架，成本是多少

不是"不能"，是"现在不值"：

- 现有 300 个函数中约 40% 是直接 DOM 操作，需要逐个改写成声明式渲染；
- 引导层、粒子背景、滚动进场这些命令式效果要包成 hook 或指令；
- `api.js` 可以原样保留（它已经是独立抽象）；
- 构建产物要与现在"改完即生效"的部署方式二选一，得先补一条 CI。

估算是**两周以上**的纯重构，期间功能冻结。所以决定是：**不迁，但把 `api.js` 这层抽象留住**，未来真要迁，请求层不用重写。

## 十二、安全设计

| 面 | 措施 | 位置 |
|---|---|---|
| 身份 | `comp_uid` 由服务端签名（itsdangerous），HttpOnly | `app.py` before_request |
| 后台 | 独立 `admin_session` cookie，签名 + HttpOnly + SameSite=Strict + Secure；角色分 `admin` / `readonly` | `_require_admin` |
| 限流 | **双桶**：用户桶（按 uid）+ 出口 IP 桶（阈值 ×20，防 NAT 误伤）；按操作分档：对话 20/分、评分补写 5/分、修订 6/分、改写 10/分、自查 30/分 | `_rate_limited(name, limit, window)` |
| 客户端 IP | 只在本机反代转发时采信 `X-Real-IP`（nginx 用 `$remote_addr` 覆盖写入）；**不采信 `X-Forwarded-For`** | `_client_ip` |
| 上传 | 需登录 + 限流 + `secure_filename` + 扩展名白名单 + 体积上限 + **zip 解压总量预检（200 MB）** | `upload_file` |
| 注入 | 全部 SQL 参数化；动态条件只拼常量与占位符 | 见第九章 |
| 输出 | 错误统一 `_friendly_error` + `_sanitize_error_detail`，堆栈只进日志 | 全局 errorhandler |
| 响应头 | CSP（`default-src 'self'`、`frame-ancestors 'self'`、`object-src 'none'`）、HSTS、X-Frame-Options、X-Content-Type-Options、Referrer-Policy | nginx + Flask |
| 服务指纹 | `server_tokens off`，响应只回 `Server: nginx` | nginx |
| 权限边界 | `/admin`、`/monitor`、`/api/history`、`/api/admin/*` 未授权一律 401 | 实测 |

一个必须记住的教训：`X-Forwarded-For` 的伪造 + cookie 可清空，两者叠加可以完全绕过限流（实测换 cookie + 伪造头连打 6 次全部通过）。修复后实测：同 cookie 第 7 次 429；换 cookie 打 111 次，第 101 次准确触发 IP 桶。

## 十三、部署与运行

```
用户 → nginx :443 (TLS 1.2/1.3, HSTS, gzip, 静态直出)
        ├─ /static/*  → /opt/comp-agent/static/   直接读盘，不经后端
        └─ /*         → proxy_pass 127.0.0.1:8080
                          gunicorn wsgi:app --workers 1 --threads 24 --timeout 600
                          systemd: comp-agent（EnvironmentFile=.env）
```

| 项 | 值 | 原因 |
|---|---|---|
| workers | **1** | 任务表、并发计数、限流桶都在进程内存里，多 worker 会各算各的 |
| threads | 24 | LLM 调用是 IO 等待，线程模型足够；实测单 key 24 路并发无 429 |
| timeout | 600 s | 深度版 p90 约 5 分钟，留余量 |
| 静态资源 | nginx 直出 | 不占 worker，也不触发限流 |

同一台机器上还有 8081/8082/8083 三个实例（预发布/对照用），只监听 127.0.0.1，公网不可达。

证书为 DigiCert DV，SAN 含 `www`，2026-12-25 到期。**这张证书是手工上传的，`certbot` 的 renewal 目录里没有它的配置，自动续期管不到它**——已加 `comp-agent-certcheck.timer`（每天 09:00 巡检，剩余不足 21 天写系统日志告警）。

部署纪律（因踩过事故而固定下来）：

1. 先 `md5sum` 比对本地与线上，相同则跳过；
2. 服务器 `cp -a` 备份带时间戳；
3. 传 `/tmp` 再 `cp` 覆盖（避免 scp 半截文件）；
4. 回读 md5 校验；
5. 静态资源改完必须 bump `?v=`，否则浏览器与 SW 缓存不更新；
6. **行尾必须按文件判**：线上 `index.html`、`app.js` 是 LF，`style.css`、`competition_agents.py` 是 CRLF；用 `tr -cd '\r' | wc -c` 判，别用 `grep -c $'\r'`（在 Git Bash 里会退化成数字母 r）。

## 十四、规模与容量边界

| 维度 | 当前实测 | 说明 |
|---|---|---|
| 代码量 | 后端 24,189 行 / 44 模块；前端 15,292 行（自有代码，另含 3 个第三方副本） | app.py 占后端 40% |
| 路由 | 134 条 | 后台 20 条，其余为业务与 API |
| 数据表 | 16 张 | 两库分离 |
| 赛事知识 | 15 个档案 + 15 份规则原文 + 范文库 | 每个档案带官方来源与核查日期 |
| 生成记录 | 333 次 | 真实使用数据 |
| 模型调用 | 461 次 / 224 万 tokens（有归属记录的部分） | 深度版单次 15.7 万 |
| 测试 | 154 项 | 含限流、上传、用量归属、目录布局、启动块 |

**容量上限的准确表述**：单 worker × 24 线程。同时进行的生成任务由 `threading.Semaphore(3)` 限制为 **3 个**，超出的进 FIFO 队列；模型调用另有一道 `_LLM_GATE(4)` 控并发，避免瞬时打爆单 key 速率。所以瓶颈**不是线程数，是同时跑的 LLM 长任务数**。以单次深度版 5 分钟计，理论吞吐约 36 次/小时；实际受模型侧速率与队列长度影响。

要扩，第一步不是加机器，而是把「任务队列、并发计数、限流桶」三样内存态挪到共享存储（Redis），否则多 worker 各自为政。当前单机规模够用，但这是明确的扩展边界。

## 十五、关键取舍

| 决策 | 为什么 | 代价 |
|---|---|---|
| LangGraph 而非顺序脚本 | 条件回边、并行扇出由框架保证；加节点不改链路 | 引入框架心智负担；并行要处理线程上下文 |
| 两条图而非一条带开关 | 简洁版 12 节点、深度版 19 节点，节点集差别大，合并要写一堆条件 | 两份构图代码，节点分工容易漂移 |
| 共享 State 而非参数传递 | 节点可插拔、可重排、下游只认字段名 | 并行时写冲突风险，必须靠"只写自己字段"的纪律 |
| 异步生成 + 同步导出 | 长任务不能占着 HTTP 连接；导出必须当场给结果 | 需要任务表、SSE、轮询、断线重连一整套 |
| 自己写 OOXML 而非模板引擎 | 章节顺序、权重加粗、双盲脱敏要动态组合 | 1300 行渲染代码要自己维护 |
| 零构建前端 | 首屏 57 KB、断网可演示、改完即生效 | 无组件化、无类型、8000 行后开始吃力 |
| 单 worker | 状态在内存，简单可靠 | 无法水平扩展 |
| SQLite 而非 MySQL | 单机、零运维、备份就是复制文件 | 并发写有锁竞争，写入必须短事务 |
| 双模型实例（0.6 / 0.2） | 写正文要发散，打分要稳定 | 两处都要包记账，漏一个就漏记一半 |

## 附录：答辩可能被问的六个架构问题

**Q1：为什么不用前端框架？**
见 10.6。核心是三句：首屏 57 KB / 0.7 秒；断网可演示、改完即生效；这套 UI 是线性流，没有需要框架解决的组件树与跨页状态。代价也认：300 个函数在全局、无类型，到 8000 行已经吃力。

**Q2：为什么只能用单 worker，能不能扩容？**
任务表、并发计数、限流桶在进程内存，多 worker 各算各的会互相踩。扩容第一步是把这三样挪到 Redis，第二步才是加机器。当前并发闸门 3 路、吞吐约 36 次/小时，够校内规模。

**Q3：生成要 5 分钟，用户关了页面怎么办？**
任务是异步的，`task_id` 已落库。重开页面可以从历史里恢复，也可以重新订阅 `/api/stream/<task_id>` 继续看进度。断线不影响后台执行。

**Q4：怎么保证生成内容不是编的？**
三层：① 写作时把赛事官方章节与评分维度注入 prompt，结构来自档案不是模型想象；② 清理链去套话、去占位符、去"待补充"段；③ 导出前质检，命中编造引用/双盲泄露直接 422 拒收。但要说清楚：**这是降低概率，不是保证**，生成结果仍需作者核实——结果页有明示。

**Q5：模型调用成本多少？**
实测深度版单次 24 次调用 / 15.7 万 tokens，简洁版 13 次 / 4.6 万。按 deepseek-chat 官方价折算，深度版一份约几毛钱。所有调用都记账，后台能按任务看单次成本与 p90。

**Q6：这套东西的技术难点在哪？**
不在"调模型写文章"，在三处工程问题：① 并行节点读不到线程上下文导致用量漏记一半（靠 `_bind_task_ctx` 逐节点包装解决）；② 篇幅闸门与写作目标不同源，导致"刚达标就被压回下沿"，要上下限同源 + 整句裁剪而不是硬截断；③ prompt 与判据不同源，补写会反复失败而分数不动。这三条都是实测踩出来的，不是设计时想到的。
